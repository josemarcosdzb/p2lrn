SEGUIMIENTO / MÉTRICAS

Métricas, progreso y analítica

P2LRN no guarda el historial de un alumno dentro del curso. El Player produce estado, puntuaciones y eventos; tu plataforma decide qué conservar, cómo asociarlo al alumno y cómo convertirlo en informes, progreso, analítica o xAPI de confianza.

1. Qué significa «sacar las métricas»

No existe un único objeto llamado «métricas». Durante una reproducción hay cuatro fuentes distintas y conviene conservarlas con finalidades diferentes.

Estado

loadState y saveState sirven para reanudar una actividad exactamente donde estaba. Es un snapshot reemplazable, no un historial.

Puntuación

reportScore entrega una puntuación normalizada cuando la actividad tiene una nota utilizable.

Eventos

emitEvent recibe el flujo cronológico p2lrn:*. Es la fuente adecuada para analítica, auditoría y series temporales.

Progresión

El Player mantiene un estado separado con viewed, completed, passed y scorePercent para aplicar las reglas del curso.

No leas métricas desde el HTML del Player ni desde el iframe SCORM/H5P.

Usa Host Adapter y los eventos públicos. El DOM visible es presentación; no es un contrato de datos.

2. Arquitectura recomendada

El Player debe permanecer independiente de tu base de datos. La aplicación que lo contiene conoce al alumno y el intento actual; el Host Adapter une esa identidad privada con los identificadores portables que entrega P2LRN.

Alumno / intento+context P2LRN→Host Adapter→API de tu plataforma→estado / notas / eventos / LRS

La identidad del alumno, la matrícula, el grupo, la convocatoria y el identificador de intento son datos de tu plataforma. No se escriben dentro del .p2lrn y P2LRN no impone su formato.

3. Cómo identificar de qué actividad procede cada dato

El context del Player utiliza identificadores del paquete y del grafo. La combinación sirve para relacionar una métrica con la versión exacta del contenido sin introducir IDs privados de tu LMS en el paquete.

packageId

Identidad lógica del paquete.

contentRoot

Huella de integridad del contenido. Cambia cuando cambia el contenido y evita restaurar estado sobre otra revisión por accidente.

entityId

Actividad, unidad o raíz a la que pertenece el dato.

resourceId

Recurso asociado a la actividad cuando existe.

representationId

Representación concreta que está ejecutando el Player.

rendererId

Presentación/runtime elegido para esa representación.

profile / runtime

Algunos estados de sistema, como progresión, identifican su superficie mediante estos campos.

Una clave robusta de persistencia suele combinar tu learnerId y attemptId con packageId, contentRoot, entityId y la superficie (rendererId, profile o runtime).

4. Host Adapter completo para estado, notas y eventos

Este ejemplo muestra la separación recomendada. currentUser, currentAttempt y learningApi pertenecen a tu aplicación; P2LRN sólo llama al contrato del Adapter.

JavaScript
const session = Object.freeze({
  learnerId: currentUser.id,
  attemptId: currentAttempt.id,
});

function metricKey(context) {
  return {
    learnerId: session.learnerId,
    attemptId: session.attemptId,
    packageId: context.packageId,
    contentRoot: context.contentRoot,
    entityId: context.entityId ?? null,
    surface:
      context.profile ??
      context.rendererId ??
      context.runtime ??
      'package',
  };
}

const adapter = P2LRN.createHostAdapter({
  async loadState(context) {
    return learningApi.loadState(metricKey(context));
  },

  async saveState(state, context) {
    await learningApi.saveState(metricKey(context), state);
  },

  async reportScore(score, context) {
    await learningApi.saveScore(metricKey(context), score);
  },

  async emitEvent(event, context) {
    await learningApi.appendEvent({
      ...metricKey(context),
      event,
    });
  },
});

document.querySelector('p2lrn-player').adapter = adapter;
El Adapter se ejecuta en código de confianza de tu aplicación.

No pongas tokens, endpoints privados ni identidad del alumno dentro del paquete. La API de tu plataforma debe seguir autenticando y autorizando cada escritura.

5. Qué recibe cada callback

loadState(context)

Se llama al abrir una actividad o la progresión. Devuelve el último snapshot compatible o null. No es un evento analítico.

saveState(state, context)

Recibe el estado completo que permite reanudar. Debe sustituir el snapshot anterior de esa misma clave lógica.

reportScore(score, context)

Recibe una nota estructurada. Puede llamarse más de una vez en contenidos que hacen commits sucesivos, por lo que tu política de «última», «mejor» o «por intento» pertenece a la plataforma.

emitEvent(event, context)

Recibe el sobre canónico del evento. Las llamadas se serializan en orden por Adapter; es la vía recomendada para un log analítico.

6. Sobre canónico de un evento

Todos los eventos persistibles comparten el mismo sobre. El payload cambia según el tipo de evento; context permite atribuirlo a la actividad correcta.

JSON
{
  "schema": "https://p2lrn.org/schema/runtime-event/1",
  "version": "1",
  "type": "p2lrn:score",
  "timestamp": "2026-10-16T08:30:00.000Z",
  "context": {
    "packageId": "urn:uuid:...",
    "contentRoot": "sha256:...",
    "entityId": "urn:uuid:...",
    "resourceId": "urn:uuid:...",
    "representationId": "urn:uuid:...",
    "rendererId": "https://p2lrn.org/renderer/questionnaire/standard"
  },
  "payload": {
    "graded": true,
    "raw": 8,
    "max": 10,
    "normalized": 0.8
  }
}

En listeners DOM, los campos del payload se mantienen también directamente en event.detail por comodidad y el sobre completo aparece en event.detail.event. En HostAdapter.emitEvent() recibes directamente el sobre canónico.

7. Métricas de cuestionarios y juegos nativos

Los cuestionarios y los juegos basados en cuestionario comparten la misma sesión. Por eso puedes obtener respuestas, avance, tiempo, intentos, puntuación final y detalle por pregunta sin inspeccionar la interfaz.

p2lrn:answer

Incluye questionId y la respuesta normalizada de esa pregunta.

p2lrn:progress

Incluye value de 0 a 1, answered y total. Es progreso dentro del cuestionario, no porcentaje del curso completo.

p2lrn:statechange

Snapshot con respuestas, pregunta actual, número de intentos terminados, puntuación guardada, estado de juego y temporización.

p2lrn:timeupdate

Expone tiempo restante del intento y de la pregunta cuando existen límites de tiempo.

p2lrn:timeout

Indica si agotó el tiempo el intento completo o una pregunta concreta.

p2lrn:score

Entrega nota total y desglose por pregunta.

p2lrn:complete

Entrega puntuación, respuestas finales y el motivo de finalización.

La puntuación nativa tiene este formato. normalized va de 0 a 1 cuando la corrección es automática; si el modo de corrección pertenece al host, graded es false y normalized es null.

JSON · score
{
  "graded": true,
  "raw": 8,
  "max": 10,
  "normalized": 0.8,
  "questions": [
    {
      "questionId": "q1",
      "graded": true,
      "correct": true,
      "hits": 1,
      "errors": 0,
      "pointsAwarded": 2,
      "pointsPossible": 2
    }
  ]
}

Si necesitas «aciertos por pregunta», «errores», «puntos obtenidos» o «preguntas sin responder», usa score.questions y el estado/respuestas; no intentes reconstruirlo desde el texto que ve el alumno.

8. Métricas SCORM 1.2 y SCORM 2004

SCORM mantiene su modelo CMI. P2LRN conserva ese estado y lo entrega mediante saveState y p2lrn:statechange. El objeto contiene state.values; las claves exactas dependen de la versión y de lo que el SCO realmente escriba.

SCORM 1.2

Nota: cmi.core.score.raw, max, min. Estado: cmi.core.lesson_status. Posición: cmi.core.lesson_location. Tiempo: cmi.core.session_time y cmi.core.total_time.

SCORM 2004

Nota: cmi.score.raw, max, min, scaled. Estado: cmi.completion_status y cmi.success_status. Progreso: cmi.progress_measure. Posición: cmi.location. Tiempo: cmi.session_time y cmi.total_time.

Interacciones

cmi.interactions.* puede contener id, tipo, respuesta del alumno, resultado, latencia, respuestas correctas y objetivos cuando el SCO los publica.

Objetivos

cmi.objectives.* conserva objetivos y sus notas/estados cuando el paquete los utiliza.

P2LRN deriva reportScore al hacer Commit o Terminate si hay una nota utilizable y ha cambiado. Para SCORM 2004 usa primero cmi.score.scaled; si no existe, puede normalizar raw / max. El campo passed sale de cmi.success_status en 2004 o de cmi.core.lesson_status en 1.2.

No todos los SCORM rellenan todas las métricas.

Que el runtime soporte una clave CMI no significa que el curso la escriba. Guarda el estado recibido y trata cada campo como opcional.

9. Métricas H5P y xAPI

H5P comunica estado para reanudación y también puede emitir xAPI. P2LRN reenvía cada statement como p2lrn:xapi y, cuando el statement contiene resultado, deriva una puntuación común para que tu plataforma no tenga que interpretar cada tipo H5P sólo para obtener la nota básica.

p2lrn:statechange

Estado H5P obtenido del runtime para reanudar la actividad.

p2lrn:xapi

Incluye el statement original en payload.statement, además de runtime:"h5p", source:"content-runtime" y authoritative:false.

p2lrn:score

Deriva raw, max, normalized, passed y completed desde statement.result cuando están disponibles.

reportScore

Se llama para xAPI terminal con verbos completed, passed o failed. El score sigue marcado como no autoritativo.

p2lrn:complete

Se emite al recibir uno de esos verbos terminales e incluye el statement y la puntuación derivada.

El xAPI producido por el contenido no es una declaración autenticada de tu plataforma.

Antes de enviarlo a un LRS, reconstruye en el servidor el actor, authority, registration/attempt y cualquier otro dato que pertenezca a tu LMS. No confíes en identidad introducida por el contenido.

10. Métricas de progresión del curso

La progresión utiliza un estado separado de los estados internos de cada actividad. El Player lo recalcula a partir de rendered, finalización y puntuación, lo guarda mediante Host Adapter y emite p2lrn:progressionchange cuando cambia.

JSON · p2lrn-progression-state/1
{
  "version": "p2lrn-progression-state/1",
  "entities": {
    "urn:uuid:actividad-1": {
      "viewed": true,
      "completed": true,
      "passed": true,
      "scorePercent": 82.5,
      "updatedAt": "2026-10-16T08:30:00.000Z"
    }
  }
}

p2lrn:rendered puede marcar una actividad como vista; p2lrn:complete la marca completada; los scores aportan passed y scorePercent. Después se aplican required, gateFollowing, completionRequirement, minScore y unlockWhen.

p2lrn:progress no es progreso global del curso.

Ese evento expresa avance dentro de ciertas actividades, por ejemplo preguntas respondidas en un cuestionario. Para el curso usa el estado de progresión y las reglas declaradas por sus entidades.

11. Qué conviene persistir

Una plataforma suele necesitar separar el snapshot de reanudación del historial analítico. El esquema físico es tuyo, pero estas responsabilidades evitan mezclar datos que tienen ciclos de vida distintos.

Estado actual

Un registro por alumno/intento/actividad/superficie. Se reemplaza con cada saveState.

Puntuaciones

Guarda cada reporte por intento o aplica explícitamente tu política de última/mejor nota. P2LRN no decide esa política.

Eventos

Log opcional append-only con el sobre canónico, más un receivedAt del servidor.

Intento

Entidad de tu plataforma con inicio, cierre, matrícula, usuario y reglas de negocio. No forma parte del paquete.

Para reanudar con seguridad, incluye contentRoot en la clave. Si el contenido cambia, puedes decidir migrar el estado o iniciar un intento compatible en lugar de aplicar silenciosamente un snapshot de otra versión.

12. Tiempo, frecuencia y volumen de eventos

Los eventos de alta frecuencia no deben convertirse automáticamente en una escritura SQL por segundo. p2lrn:timeupdate, respuestas o commits sucesivos pueden agruparse según tus necesidades.

  • Usa saveState para el último snapshot, no como tabla histórica infinita.
  • Si quieres analítica temporal, persiste emitEvent de forma asíncrona o por lotes.
  • Guarda el timestamp del evento y añade un receivedAt del servidor. El primero viene del runtime del navegador; el segundo pertenece a tu infraestructura.
  • Para «tiempo de sesión» de negocio, mide también apertura/cierre del intento en tu servidor. No dependas únicamente del reloj o del contenido del navegador.
  • En SCORM conserva los tiempos CMI cuando el SCO los publique; en cuestionarios temporizados conserva el estado de timing; en H5P conserva cualquier duración xAPI sólo como dato generado por contenido.

13. Duplicados, reintentos e idempotencia

emitEvent se entrega en orden dentro de un mismo Adapter, pero el sobre P2LRN no pretende ser el identificador durable de tu base de datos. Si tu transporte puede reintentar peticiones, añade una clave de ingestión propia en el servidor.

Una estrategia habitual es generar un identificador al recibir el evento y, cuando necesites deduplicación determinista, combinar intento + tipo + timestamp + contexto + hash del payload. La política exacta depende de si tu analítica quiere conservar repeticiones legítimas.

14. Recetas rápidas

Quiero la nota final

Implementa reportScore. Conserva raw, max, normalized, passed/completed cuando existan.

Quiero reanudar donde estaba

Implementa loadState + saveState y conserva el snapshot por intento/actividad.

Quiero analítica por pregunta

En cuestionarios usa p2lrn:answer, score.questions y el complete.answers final.

Quiero interacciones SCORM

Lee las claves cmi.interactions.* del estado guardado. No todos los paquetes las rellenan.

Quiero xAPI H5P

Consume p2lrn:xapi, conserva el statement como entrada de contenido y reconstruye identidad/authority en tu servidor antes del LRS.

Quiero saber qué está desbloqueado

Conserva el estado p2lrn-progression-state/1 y deja que el Player aplique las reglas del paquete.

15. Privacidad y confianza

El paquete P2LRN es portable y no debe contener el historial personal del alumno. El Host Adapter pertenece al host de confianza. Los eventos de contenido pueden describir lo que hizo una actividad, pero la identidad, matrícula, intento, permisos y autoridad final pertenecen a tu plataforma.

Para detalles de cada evento consulta Eventos; para las reglas de finalización consulta Progresión; para la conexión completa con tu aplicación consulta Integración.
