Módulo LTI 1.3 de P2LRN

LTI 1.3 permite que una plataforma educativa abra un recurso P2LRN con una sesión verificada y, cuando proceda, intercambie calificaciones. Es una integración entre LMS y servidor, no una característica añadida dentro del ZIP del curso.

Arquitectura: un único Player

LMS→Gateway LTI 1.3→Host Adapter→Player

El LMS conserva estudiantes, docentes, matrículas y libreta de calificaciones. El gateway comprueba la identidad y selecciona el contenido publicado; el Host Adapter gestiona carga y guardado de estado, eventos y notas. Player abre siempre el mismo .p2lrn, independientemente del fabricante del LMS.

OIDC: inicio y lanzamiento seguro

  1. El administrador registra de forma explícita la plataforma mediante issuer, client_id, deployment_id y URLs confiables.
  2. Cuando un usuario abre la actividad, comienza el inicio de sesión OIDC. El gateway genera una transacción con state y nonce únicos.
  3. El LMS devuelve un id_token firmado. El servidor valida firma y claims, incluida la audiencia, versión, tipo de lanzamiento y URI de destino.
  4. Se consumen state y nonce de manera atómica para impedir reutilización, y sólo se inicia la sesión del contenido publicado autorizado.

Estas comprobaciones no deben realizarse sólo en JavaScript del navegador: corresponden al backend confiable.

JWKS y claves públicas

JWKS permite obtener las claves públicas con las que comprobar las firmas. El gateway únicamente debe aceptar URLs JWKS de plataformas previamente registradas y aprobadas; no puede confiar en la dirección suministrada por un JWT desconocido.

El proveedor también tendrá que publicar sus claves públicas para firmar respuestas de Deep Linking y autenticarse ante los servicios del LMS, con rotación controlada.

Deep Linking: elegir curso y lección

Un profesor podrá seleccionar un curso, unidad o actividad desde un catálogo P2LRN de recursos publicados. La selección genera un enlace de tipo ltiResourceLink con un p2lrn_binding_id opaco vinculado a la institución, registro, despliegue, paquete y revisión del contenido.

Identidad portable

packageId + contentRoot + entityId identifica el contenido elegido y su revisión.

Identidad de despliegue

El vínculo opaco se guarda por institución y despliegue. No depende únicamente del resource_link.id de la plataforma.

Copias de cursos

Si el LMS duplica un curso, la referencia al contenido no debe depender de un ID de actividad que podría cambiar.

La firma de Deep Linking y el selector real requieren un backend y catálogo que todavía no se han completado.

AGS: enviar calificaciones

AGS (Assignment and Grade Services) es el servicio LTI para comunicar resultados al libro de notas del LMS. El navegador puede notificar una puntuación al Host Adapter, pero el backend debe validarla de forma autoritativa según la evaluación y el intento antes de enviarla.

El envío requiere scopes autorizados y tokens OAuth adecuados, con control de reintentos e idempotencia para evitar notas duplicadas. Si una plataforma no concede AGS, el contenido puede reproducirse, pero no se debe prometer sincronización automática de notas.

NRPS: roles y matrículas (opcional)

NRPS (Names and Role Provisioning Services) permite consultar roles y miembros cuando el LMS expone ese servicio, la institución lo autoriza y es necesario. No sustituye el control local de permisos ni obliga a copiar listas de alumnos al paquete P2LRN.

Qué existe y qué falta implementar

Existe: Player y Host Adapter

Reproducción del paquete y contrato de loadState, saveState, reportScore, emitEvent y resolveResourceUrl.

Existen contratos LTI iniciales

integration/lms/launch-contract.mjs define enlaces, identidad versionada y borradores de AGS; integration/lms/host-adapter.mjs conecta el Player a una API de gateway. Hay pruebas de contrato.

Pendiente: proveedor P2LRN LTI real

Faltan registro persistente por institución, comprobación OIDC/JWKS, sesiones, endpoints operativos, catálogo y selector Deep Linking firmado, AGS real y NRPS opcional.

Pendiente: interoperabilidad E2E

No se han certificado con P2LRN todos los flujos en Moodle, Canvas, Sakai, Chamilo y Open edX.

No son endpoints publicados

Las rutas /lti/login, /lti/launch y /lti/jwks aparecen en el diseño técnico, pero no deben registrarse en un LMS real hasta disponer de un gateway desplegado y validado.

Seguridad y aislamiento multiinstitución

  • Validar criptográficamente JWT y comprobar iss, aud, azp, exp, iat, nonce, state, versión, tipo de mensaje y deployment_id.
  • Consumir cada transacción una sola vez; prevenir replay y acceso entre instituciones o despliegues.
  • Particionar el progreso por institución, despliegue, vínculo, alumno, intento, paquete, revisión y actividad.
  • No exponer claves privadas, credenciales del LMS, datos personales ni tokens dentro de un .p2lrn o URLs del navegador.
  • Rechazar cualquier acceso a un contenido no publicado, actividad inexistente o servicio no autorizado.
  • Verificar en servidor los resultados antes de transmitir notas oficiales.

Proceso de validación para producción

  1. Implementar registros, OIDC y JWKS con claves auditables, rotación y sesión transaccional.
  2. Conectar el catálogo de cursos publicados y respuestas Deep Linking firmadas.
  3. Persistir progreso y resultados por alumno y recurso, incorporando un outbox AGS idempotente.
  4. Validar los flujos completos en LMS reales: docente, alumno, copias de curso, reanudación, expiración, accesos denegados y libro de notas.
  5. Comprobar accesibilidad, dispositivos móviles, juegos, SCORM, H5P y regresiones frente a las capacidades existentes.
