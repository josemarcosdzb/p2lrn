CONECTORES / LTI 1.3

Módulo LTI 1.3 de P2LRN

P2LRN permite que el profesor añada cursos interactivos a su aula desde la herramienta instalada por el centro. El administrador configura la conexión una vez; después, docentes y alumnos trabajan desde el propio LMS. Esta guía separa los pasos de uso de los requisitos de instalación y seguridad.

Para profesores: añadir un curso al aula

  1. Entra en tu asignatura y elige la actividad o herramienta P2LRN que haya instalado tu centro.
  2. Selecciona un curso disponible o sube uno desde el selector, si tu centro habilita esa opción.
  3. Confirma «Añadir curso» y regresa a la asignatura.
  4. Abre la actividad en vista de alumno para comprobar que se reproduce y que se puede completar.

Si P2LRN no aparece en el selector del LMS, solicita al administrador que active la herramienta. No necesitas configurar claves ni direcciones de servidores. Ver los detalles de publicación.

Código fuente del proveedor LTI 1.3

El ZIP técnico incluye el código actual de integration/lms: proveedor criptográfico, servidor HTTP, store SQLite, cliente AGS, contratos de lanzamiento y pruebas. También incluye el Host Adapter necesario para la frontera con Player. No es un plugin específico de Moodle/Canvas/Sakai/Chamilo/Open edX ni un binario precompilado.

Requisitos

Node.js 22.13+ y distribuciones compiladas de Toolkit y Player. Para un despliegue real se necesita además una clave RSA persistente, almacenamiento privado y un proxy HTTPS de confianza.

Servidor

node integration/lms/lti-server.mjs inicia el proveedor después de configurar sus variables de entorno. Por defecto escucha en loopback.

Seguridad e interoperabilidad

El proveedor contempla validación JWT, issuer/audience, nonce/state, protección frente a replay, Deep Linking, persistencia, Player, AGS OAuth y aislamiento entre instituciones.

Self-hosted no significa servicio público compartido

p2lrn.org no es un gateway LTI multiinstitución para registrar directamente en un LMS. Cada despliegue debe alojar el proveedor en una URL HTTPS propia, conservar sus claves y registrar explícitamente sus plataformas de confianza.

Guía práctica: conectar P2LRN con un LMS

El proceso requiere dos registros coordinados: instalar el proveedor P2LRN y registrar esa herramienta dentro del LMS. Después debes registrar en P2LRN los datos reales del LMS. Ni descargar un ZIP ni copiar una URL abre por sí solos un curso.

  1. Preparar Node.js, Toolkit, Player, claves y almacenamiento privado.
  2. Publicar el proveedor en un dominio HTTPS.
  3. Crear una herramienta externa LTI 1.3 en Moodle, Canvas u otro LMS compatible.
  4. Registrar en el proveedor el issuer, client ID, deployment ID, endpoints y JWKS reales del LMS.
  5. Publicar el curso .p2lrn y seleccionarlo desde el LMS mediante Deep Linking o un binding administrativo.
  6. Probar el acceso como docente y alumno y, si procede, enviar una nota autorizada por AGS.

¿Dónde funciona LTI? La web pública de P2LRN es documentación, no un servicio LTI multiinstitución ya listo para registrar. El proveedor se instala en un servidor controlado por tu organización. Utiliza almacenamiento SQLite privado para registros, sesiones, estados y entregas AGS; no es el índice de archivos de Analytics ni modifica el curso .p2lrn.

1. Preparación e instalación del proveedor LTI 1.3

Requisitos contrastados: Node.js 22.13 o posterior, código fuente del repositorio, compilaciones de Toolkit y Player, clave privada RSA persistente, token administrativo secreto y un directorio privado con permisos limitados. El ZIP de descarga contiene fuentes: no es un instalador ni una herramienta LTI preconfigurada.

Desde la raíz del repositorio P2LRN, con Node.js y NPM instalados:

Terminal · desde el repositorio
cd packages/toolkit
npm ci
npm run build
cd ../..
node packages/player/scripts/build-dist.mjs

Antes de arrancar el servidor debes generar una clave RSA de 3072 bits y conservarla entre reinicios (ejemplo con OpenSSL):

Terminal · clave privada
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out /ruta/privada/p2lrn-lti.pem

Inyecta en el proceso las siguientes variables de entorno, sustituyendo rutas y dominio. Esto es una lista de variables, no un archivo .env que el servidor cargue automáticamente. Debes establecerlas con tu gestor de servicios o terminal.

Variables de entorno
P2LRN_LTI_BASE_URL=https://lti.ejemplo.edu
P2LRN_LTI_DATA_DIR=/ruta/privada/p2lrn-lti-data
P2LRN_LTI_KEY_FILE=/ruta/privada/p2lrn-lti.pem
P2LRN_LTI_ADMIN_TOKEN_FILE=/ruta/privada/token-administrador.txt
P2LRN_LTI_PORT=37891
P2LRN_LTI_HOST=127.0.0.1

P2LRN_LTI_ADMIN_TOKEN_FILE debe contener un token aleatorio de al menos 32 caracteres; mantenlo fuera del repositorio y no lo pegues en la web. Una vez establecidas las variables de entorno, arranca el servidor desde la raíz del repositorio:

Terminal · iniciar proveedor
node integration/lms/lti-server.mjs

El servidor escucha por defecto en 127.0.0.1:37891. Necesita un proxy HTTPS que exponga únicamente las rutas autorizadas. No publiques el archivo PEM, SQLite, el directorio de cursos ni /lti/admin/* sin una política administrativa estricta.

2. Configurar la herramienta LTI 1.3 dentro del LMS

En la administración de tu campus busca la opción equivalente a herramientas externas LTI 1.3. Su nombre exacto cambia según la versión de Moodle, Canvas, Sakai, Chamilo u Open edX. Elige LTI 1.3, no LTI 1.1, y registra las URLs de tu propio servidor P2LRN:

URLs de la herramienta
Tool / Launch URL: https://lti.ejemplo.edu/lti/launch
Initiate Login URL: https://lti.ejemplo.edu/lti/login
JWKS / Public keyset: https://lti.ejemplo.edu/lti/jwks
Redirect URI for launch: https://lti.ejemplo.edu/lti/launch
Deep Linking URL: https://lti.ejemplo.edu/lti/deep-link
Deep Linking redirect URI: https://lti.ejemplo.edu/lti/deep-link

Estas URLs son ejemplos, no endpoints ofrecidos por p2lrn.org. Para el inicio OIDC y Deep Linking, registra las direcciones de retorno exactas y habilita la colocación o selección de contenido. Solo si necesitas notas habilita los permisos AGS que la instalación LMS admita.

Tras guardar la herramienta, el LMS entrega su issuer, client ID y deployment ID, además de las URLs reales de autorización OIDC, token OAuth2 y el conjunto de claves públicas JWKS. Estos valores pertenecen a la instancia concreta del LMS: no copies valores de ejemplo ni asumas que sus rutas son iguales en otros servidores.

Consulta Conectores LMS para las particularidades de cada plataforma. La presencia de una opción LTI en su interfaz no certifica todavía todo el flujo.

3. Registrar en P2LRN la plataforma de confianza

Esta operación la realiza el administrador del proveedor. Guarda un archivo platform.json con los datos auténticos obtenidos del LMS. El ejemplo siguiente muestra únicamente la estructura admitida por POST /lti/admin/platforms; los marcadores no son credenciales utilizables:

JSON · platform.json
{
  "id": "centro-lms",
  "tenantId": "centro-001",
  "issuer": "https://campus.ejemplo.edu",
  "clientId": "CLIENT_ID_DEL_LMS",
  "authUrl": "https://campus.ejemplo.edu/URL_OIDC_REAL",
  "tokenUrl": "https://campus.ejemplo.edu/URL_TOKEN_REAL",
  "launchUrl": "https://lti.ejemplo.edu/lti/launch",
  "deepLinkLaunchUrl": "https://lti.ejemplo.edu/lti/deep-link",
  "jwks": { "keys": [
    {"kty":"RSA","kid":"ID_CLAVE_REAL","n":"MODULO_RSA_REAL","e":"AQAB"}
  ] },
  "deployments": ["DEPLOYMENT_ID_REAL"],
  "deepLinkReturnOrigins": ["https://campus.ejemplo.edu"],
  "status": "ACTIVE"
}

Una vez completados los valores, envíalo al servidor (ejemplo para shell POSIX; en PowerShell puedes utilizar Invoke-RestMethod con el archivo y un encabezado Bearer):

Terminal · registro administrativo
# Use a real admin token stored in a protected file.
TOKEN="$(cat /ruta/privada/token-administrador.txt)"
curl --fail-with-body -X POST https://lti.ejemplo.edu/lti/admin/platforms \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @platform.json

Comprueba la respuesta y consulta GET /lti/admin/platforms con el mismo Bearer. P2LRN rechaza emisores y despliegues no registrados; también comprueba las claves firmantes y vincula cada petición al registro correcto. Nunca desactives firma JWT, expiración, nonce o state para solucionar un fallo de registro.

4. Publicar un curso .p2lrn para esa institución

Exporta y valida primero el curso en Studio/Toolkit. El administrador envía el archivo binario real a POST /lti/admin/catalog. Los encabezados identifican la institución y el título visible:

Terminal · publicar contenido
curl --fail-with-body -X POST https://lti.ejemplo.edu/lti/admin/catalog \
  -H "Authorization: Bearer $TOKEN" \
  -H "x-p2lrn-tenant: centro-001" \
  -H "x-p2lrn-title: Curso de ejemplo" \
  -H "Content-Type: application/vnd.p2lrn+zip" \
  --data-binary @curso.p2lrn

El servidor verifica el paquete con Toolkit, aplica un límite de 64 MiB y devuelve un id de catálogo, packageId, contentRoot y número de entidades publicables. Conserva el id, porque es distinto del packageId portable. Puedes consultar el catálogo mediante GET /lti/admin/catalog/centro-001 con Bearer.

Para una unidad o actividad concreta, utiliza los entityId realmente presentes en el curso validado; no inventes rutas de página ni utilices un enlace externo arbitrario.

5. Insertar el contenido en el LMS: Deep Linking o binding

Opción recomendada: Deep Linking

  1. El profesor abre la herramienta P2LRN en el selector de contenidos del LMS.
  2. El LMS inicia OIDC y envía un lanzamiento firmado de tipo Deep Linking a /lti/deep-link.
  3. P2LRN muestra únicamente cursos, unidades y actividades publicadas para esa institución.
  4. El profesor elige un recurso y P2LRN devuelve al LMS una respuesta Deep Linking firmada.
  5. El LMS añade la actividad. Al abrirla, utiliza el binding opaco que identifica el curso, la revisión y la entidad seleccionada.

Alternativa: binding manual autorizado

Si el LMS admite herramientas LTI 1.3 pero no permite Deep Linking, un administrador de P2LRN puede crear el vínculo:

JSON · POST /lti/admin/bindings
{
  "registrationId": "centro-lms",
  "deploymentId": "DEPLOYMENT_ID_REAL",
  "catalogId": "ID_DEVUELTO_AL_PUBLICAR",
  "entityId": "ID_REAL_DE_CURSO_UNIDAD_O_ACTIVIDAD"
}

La respuesta proporciona bindingId y customParameters.p2lrn_binding_id. Configura ese valor como parámetro personalizado p2lrn_binding_id en la actividad LTI del LMS. Debe viajar en el claim LTI custom. Un alumno no puede escoger libremente otro curso escribiendo un ID o una URL.

6. Qué ocurre al abrir la actividad como alumno

  1. El alumno inicia sesión en su LMS y abre la actividad añadida por el profesor.
  2. El LMS llama a /lti/login; P2LRN crea una transacción con state y nonce de un solo uso.
  3. El LMS devuelve un id_token firmado a /lti/launch; el proveedor verifica su firma, emisor, audiencia, despliegue, expiración y binding autorizado.
  4. Se crea una sesión limitada, con cookies protegidas y control CSRF. El servidor entrega el paquete ya autorizado y abre el mismo P2LRN Player.
  5. El Host Adapter utiliza /lti/runtime/state/load, /lti/runtime/state/save, /lti/runtime/event y /lti/runtime/score para gestionar estado, eventos y observaciones autorizadas.

El estado se separa por institución, registro, despliegue, binding, usuario, intento, contenido y revisión. El servidor LTI utiliza almacenamiento privado SQLite para estos datos. Esto no implica que Analytics reciba automáticamente archivos .p2lrn-result: el flujo de resultados de Analytics es diferente y no debe describirse como integrado sin una prueba específica.

7. Calificaciones AGS: observación frente a nota oficial

El Player puede reportar puntuaciones, pero una puntuación del navegador no se convierte sola en una nota del LMS. Tras evaluar el intento, un administrador autorizado consulta GET /lti/admin/attempts?tenantId=centro-001 y aprueba una nota con POST /lti/admin/grades:

JSON · aprobar nota
{
  "attemptId": "ID_REAL_DE_INTENTO",
  "normalized": 0.85,
  "completed": true
}

normalized es una puntuación entre 0 y 1. El servidor prepara el envío mediante OAuth2 con permisos AGS. Puede reutilizar una columna compatible si el LMS concede lineitem.readonly; crear una nueva requiere el scope lineitem. El envío de puntuaciones requiere el scope score.

Si la plataforma está desconectada o falta un permiso, se conserva una operación pendiente en GET /lti/admin/ags/pending. El administrador puede reintentar mediante POST /lti/admin/ags/retry con {"outboxId":"ID_REAL"}. Revisa la nota finalmente en el libro de calificaciones del LMS; una respuesta del navegador no equivale a entrega confirmada.

Repite la prueba en la versión e instancia concretas que utilizarás de Moodle, Canvas, Sakai, Chamilo u Open edX. Las pruebas locales verifican contratos, pero no certifican todas las versiones, navegadores, políticas de iframes o servicios de esos LMS.

9. Problemas habituales, límites y seguridad

OIDC / launch rechazado (403)

Comprueba issuer, client ID, deployment ID, firma JWKS, audience, expiración y que los endpoints pertenecen a la instalación registrada. No aceptes claves de un token desconocido.

Iframe en blanco o sesión perdida

Revisa el proxy HTTPS, cookies Secure/SameSite/Partitioned, CSP y las políticas de almacenamiento y terceros del navegador/LMS. El modo HTTP solo sirve en laboratorio loopback con configuración explícita.

Selector sin cursos

Comprueba que el curso fue publicado en el tenantId correcto, que el paquete supera validación y que el profesor utiliza el despliegue permitido.

No aparece la nota en el LMS

Verifica el intento aprobado, los permisos AGS, la columna autorizada y la cola de envíos pendientes. No confundas un score observado con una calificación oficial.

Roles y matrículas

NRPS 2.0 está implementado: exige un lanzamiento LTI válido, permiso y contexto coincidente. Cada LMS necesita configuración y prueba de lectura real.

Descarga de código fuente

El ZIP LTI proporciona los archivos de implementación y pruebas; requiere construir dependencias y configurar el servidor. No es un instalador automático ni un plugin específico de un LMS.

Conserva los secretos fuera de la web pública, mantén sesiones y datos privados, restringe la API administrativa y no prometas interoperabilidad certificada sin pruebas E2E reales.

Arquitectura: un único Player

LMS→Gateway LTI 1.3→Host Adapter→Player

El LMS conserva estudiantes, docentes, matrículas y libreta de calificaciones. El gateway comprueba la identidad y selecciona el contenido publicado; el Host Adapter gestiona carga y guardado de estado, eventos y notas. Player abre siempre el mismo .p2lrn, independientemente del fabricante del LMS.

OIDC: inicio y lanzamiento seguro

  1. El administrador registra explícitamente la plataforma mediante issuer, client_id, despliegues permitidos, URLs de autorización/token y claves JWKS confiables.
  2. /lti/login crea una transacción con state y nonce únicos y de vida corta.
  3. /lti/launch valida la firma RS256 y los claims iss, aud/azp, exp, iat, versión, tipo, deployment_id, target_link_uri y binding autorizado.
  4. state y nonce se consumen para bloquear replay antes de crear la sesión de runtime.

Estas comprobaciones viven en el backend. El navegador sólo recibe una sesión limitada para el contenido ya autorizado.

JWKS y claves públicas

El proveedor publica su conjunto de claves en /lti/jwks y firma respuestas de Deep Linking con su clave RSA persistente. Para validar al LMS sólo utiliza claves pertenecientes a registros administrativos de confianza; una URL recibida desde un JWT desconocido no se convierte en fuente confiable.

Las claves privadas, el token administrativo, SQLite y el catálogo de paquetes permanecen fuera de la web pública y fuera de cada .p2lrn.

Deep Linking: elegir curso y lección

El servidor implementa catálogo y selector protegido. Un profesor puede elegir un curso, unidad o actividad publicada y el proveedor devuelve un ltiResourceLink firmado con un p2lrn_binding_id opaco ligado a tenant, registro, despliegue, paquete, contentRoot y entidad.

Identidad portable

packageId + contentRoot + entityId identifica contenido y revisión.

Binding de despliegue

El vínculo opaco evita confiar únicamente en resource_link.id, que puede cambiar al copiar cursos.

Sin Deep Linking

Un administrador puede crear un binding manual autorizado mediante POST /lti/admin/bindings y configurar su valor opaco como parámetro personalizado del LMS.

Ni el profesor ni el alumno pueden elegir una URL o entidad arbitraria para saltarse el catálogo autorizado.

AGS: enviar calificaciones

El proveedor implementa Assignment and Grade Services. El navegador puede reportar una observación, pero una nota oficial sólo se envía después de que el servidor la valide como autoritativa. POST /lti/admin/grades registra la decisión y utiliza un outbox persistente e idempotente para el envío OAuth2.

Columna existente

Con scope lineitem.readonly puede localizar y reutilizar una columna compatible del mismo resourceLinkId, respetando su scoreMaximum.

Crear columna

Sólo se crea una nueva cuando el LMS concedió explícitamente el scope de escritura lineitem.

Reintentos

Los fallos permanecen en /lti/admin/ags/pending y pueden reintentarse sin aceptar redirecciones o destinos ajenos al LMS registrado.

NRPS 2.0: consultar matrículas y roles del curso

P2LRN incorpora Names and Role Provisioning Services 2.0 como lectura opcional. Puede consultar alumnos y profesores matriculados aunque todavía no hayan abierto una actividad. No modifica las matrículas y no almacena permanentemente los listados de alumnos.

Activar NRPS en el LMS

  1. Registrar la herramienta LTI 1.3 y habilitar Names and Role Provisioning Services si la versión del LMS lo permite.
  2. Autorizar el scope https://purl.imsglobal.org/spec/lti-nrps/scope/contextmembership.readonly.
  3. El lanzamiento LTI firmado debe contener el claim https://purl.imsglobal.org/spec/lti-nrps/claim/namesroleservice, con service_versions: ["2.0"] y context_memberships_url.
  4. Si el servicio usa otro origen HTTPS, registrarlo expresamente en nrpsAllowedOrigins. P2LRN nunca acepta una URL arbitraria enviada por el navegador.
JSON · claim LTI
{
  "https://purl.imsglobal.org/spec/lti-nrps/claim/namesroleservice": {
    "context_memberships_url": "https://campus.ejemplo.edu/courses/123/memberships",
    "service_versions": ["2.0"]
  }
}

Consultar las matrículas

Un docente con rol verificado puede consultar GET /lti/runtime/nrps/memberships desde su sesión LTI. El alumno recibe 403. Un administrador del proveedor, con Bearer privado, puede listar los contextos descubiertos o leer una clase concreta:

API · solo administración
GET /lti/admin/nrps/contexts?tenantId=centro-001
GET /lti/admin/nrps/memberships?tenantId=centro-001&registrationId=centro-lms&deploymentId=DEPLOYMENT_REAL&contextId=CURSO_REAL
Authorization: Bearer TOKEN_PRIVADO

Los identificadores son los reales del registro y lanzamiento del LMS. La respuesta devuelve identificador de contexto, usuarios, roles, estado y datos opcionales permitidos por el LMS. Analytics puede seguir leyendo .p2lrn-result sin NRPS; conocer una matrícula no acredita automáticamente la autoría de un archivo offline.

Seguridad y pruebas

El proveedor solicita un token OAuth2 de solo lectura, verifica el contexto, origen, esquema y paginación, y limita tamaño de respuesta y número de usuarios. No expone listados ni tokens en los cursos.

Verificación actual: las pruebas locales del cliente NRPS y de las rutas HTTP permiten comprobar los contratos técnicos, pero no certifican una lectura real de matrículas en cada LMS. Antes de habilitar NRPS en Moodle, Canvas, Sakai, Chamilo u Open edX, el administrador debe verificar la URL OAuth2 registrada, el contexto, los permisos y los ámbitos de solo lectura, y realizar una consulta de extremo a extremo. Consulta la especificación oficial 1EdTech.

Estado actual del proveedor

Implementado: proveedor y persistencia

createP2LRNLtiProvider(), createP2LRNLtiServer() y SQLite persistente para registros, despliegues, catálogo, bindings, transacciones, sesiones, intentos, estado, eventos y outbox AGS.

Implementado: OIDC, JWKS y Deep Linking

Firma/verificación JWT, state/nonce/replay, catálogo, selector y respuesta Deep Linking firmada.

Implementado: Player, estado y AGS

Runtime autorizado, carga/guardado de estado y eventos, inspección de intentos, OAuth2 AGS, reutilización segura de lineitems y reintentos persistentes.

Implementado: lectura NRPS 2.0

Consulta de matrículas por contexto mediante OAuth2 con validación de identidad y permisos. Pendiente de prueba E2E real por LMS.

Endpoints reales del servidor self-hosted

El servidor implementa /lti/login, /lti/launch, /lti/deep-link, /lti/deep-link/confirm, /lti/jwks, /lti/health, runtime y administración. Esas rutas pertenecen a tu despliegue del proveedor, no a la web estática de P2LRN.

Seguridad y aislamiento multiinstitución

  • Validar criptográficamente JWT y comprobar iss, aud, azp, exp, iat, nonce, state, versión, tipo de mensaje y deployment_id.
  • Consumir cada transacción una sola vez; prevenir replay y acceso entre instituciones o despliegues.
  • Particionar el progreso por institución, despliegue, vínculo, alumno, intento, paquete, revisión y actividad.
  • No exponer claves privadas, credenciales del LMS, datos personales ni tokens dentro de un .p2lrn o URLs del navegador.
  • Rechazar cualquier acceso a un contenido no publicado, actividad inexistente o servicio no autorizado.
  • Verificar en servidor los resultados antes de transmitir notas oficiales.

Flujo docente y alumno implementado

Registro administrativo

El administrador registra una plataforma y despliegues explícitos, catálogo y bindings; emisores/despliegues desconocidos se rechazan.

Selección del profesor

Deep Linking muestra sólo contenido publicado y devuelve un recurso firmado ligado a la revisión.

Lanzamiento del alumno

OIDC/JWT valida identidad y despliegue, crea una sesión limitada y abre el mismo Player P2LRN.

Estado y resultados

El runtime persiste estado/eventos por sesión e intento. Una decisión de nota validada puede enviarse a AGS mediante el outbox.

Este circuito está cubierto por pruebas HTTP automatizadas del proveedor. La comprobación contra cada LMS real debe realizarse además en la instalación y versión que vaya a utilizarse.

Comprobación antes del despliegue

  1. Construir Toolkit y Player, generar una clave RSA persistente y desplegar el servidor tras HTTPS; no exponer el token administrativo, la clave privada, SQLite ni el directorio de paquetes.
  2. Registrar issuer, client ID, deployment ID, URLs y JWKS de la instancia LMS real; comprobar /lti/health y /lti/jwks.
  3. Publicar un .p2lrn real en el catálogo y verificar Deep Linking o binding manual autorizado.
  4. Probar profesor y alumno: login, launch, Player, reanudación, expiración, replay, acceso denegado y copia de curso.
  5. Cuando haya AGS, comprobar la columna y la nota en el libro real. No declarar compatibilidad NRPS con un LMS concreto sin probar una lectura real.
  6. Repetir la matriz con cuestionarios, juegos 3D, SCORM/H5P, móvil y políticas de cookies/iframes de la versión concreta del LMS.
